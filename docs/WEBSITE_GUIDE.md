# MayaCardio Signal Operations - Website Guide

## What has been added

The `frontend/` directory contains a React + TypeScript + Vite website with a public landing page and operational dashboard. The dashboard never fills cards with hardcoded counters. Its **explicitly requested synthetic demo fixture** is generated deterministically, persisted as JSON Lines and into both SQLite stores, and then all dashboard screens read the stored records through FastAPI. Live sensor-pipeline sessions remain separate from this presentation fixture.

### Pages

- **Home** - project introduction and system overview.
- **Dashboard** - device/cloud sample counts, upload backlog when the local device DB is available, processing results, sessions, loss records, integrity events, API-host resource snapshots, and personal display/refresh preferences under Settings & help.
- **Architecture** - component boundaries and data flow.
- **Security** - credential boundaries, synthetic-data scope, and deployment responsibilities.
- **Documentation** - developer resources and a link to the local API reference.

Unavailable device metrics are shown as unavailable, not as zero. Resource metrics state that they describe the host running the API, not automatically the Raspberry Pi.


## Populate a professional dashboard for a presentation

A freshly extracted project may show empty sessions because runtime databases are intentionally not packaged. For an immediate and repeatable presentation, start FastAPI and Vite as described above, open the dashboard, and click **Load demo dataset** in the Overview notice. Alternatively open Settings & help and use **Generate and store fixture**.

The repository includes `data/fixtures/synthetic_demo_seed7.jsonl`, generated by a fixed-seed algorithm and checked by a SHA-256 manifest. On first use, the API validates that source and copies its records to the runtime file `data/synthetic_demo_dataset.jsonl`. It then inserts the same sample rows, loss record, window-mode assignments, and derived processing results into `data/device.db` and `data/cloud.db`. If the bundled source file is intentionally omitted from another source distribution, the deterministic generator is the fallback. The fixture is a 30-second synthetic session at 400 Hz with 23,960 stored sample rows, 30 processing windows, one explicitly recorded 40-sample gap on Sensor 2 (indexes 4,800-4,839), and windows 15-17 assigned offline to make online/offline presentation visible. The results are derived by the repository's processing engine from the stored synthetic data. Repeated clicks verify/reuse the fixed session instead of appending duplicates.

When loaded, use **Overview** for counts and charts, **Sessions** to open `maya-demo-seed7-v1`, **Processing results** to inspect the one-second windows, **Data integrity** to show the explicit gap, and **Settings & help** to see per-database counts, download the JSONL source, or reset this single demo session. The source file is ignored by Git because it is generated locally; the deterministic generator and seed operation are committed, so another reviewer can reproduce it with the button.

This is a labelled, deterministic **website presentation fixture**. It is not a dataset from a patient, not the official `biosignal-mock`, and not proof of runtime acquisition, cloud sync deadlines, ARM64 resource use, or power-cut behavior. Demo fixture mutation/download endpoints are enabled by default only in development/test environments.

## Prerequisites

- Python 3.11 or newer (Python 3.13 is supported by the project metadata and the current Python tests).
- Node.js 22.12 or newer (recommended: current Node.js 22 LTS patch) with npm. Vite 8 requires Node.js 20.19+ or 22.12+.
- Git only if publishing to GitHub.

Docker is not required for native local development.

## Run the full stack on Windows

Open the repository root in VS Code. Keep each process in a separate terminal.

### Terminal 1 - cloud API

```powershell
.\.venv\Scripts\Activate.ps1
New-Item -ItemType Directory -Force .\data | Out-Null
$env:CLOUD_DB_PATH = ".\data\cloud.db"
$env:CLOUD_API_TOKEN = "demo-only-change-me"
python -m uvicorn pipeline.cloud_app:app --host 127.0.0.1 --port 8000
```

The token is localhost-demo-only. Remote ingestion fails closed if the cloud token is absent. Do not use this demo token on a shared or public deployment.

### Terminal 2 - frontend development server

```powershell
Set-Location .\frontend
npm install
npm run dev
```

Open the URL printed by Vite (normally `http://127.0.0.1:5173`). Vite proxies `/api`, `/health`, `/docs`, and `/openapi.json` to FastAPI on port 8000. Keep both processes running.

### Terminal 3 - development mock and device pipeline

For a local synthetic demo, start the development-only mock immediately before the pipeline as described in the root README and `docs/STEP_BY_STEP_RUN_AND_GITHUB.md`. The mock has a limited unread-data buffer; starting it long before the collector can create recorded sample gaps.

The UI displays records actually returned by the API. To populate an empty dashboard for a presentation, explicitly load the persistent, deterministic synthetic fixture described above.

## Production static build

From `frontend/`:

```powershell
$env:PUBLIC_SITE_URL = "https://YOUR-REAL-HOSTNAME"
$env:VITE_PUBLIC_SITE_URL = "https://YOUR-REAL-HOSTNAME"
$env:VITE_API_DOCS_ENABLED = "false"
npm run build
```

Replace the hostname placeholder with the actual public origin. The build generates a sitemap and robots file for the configured origin. Without an origin, it creates a development sitemap without an invented hostname.

The static output is `frontend/dist/`. When this directory exists, FastAPI serves it at `/`. FastAPI's API reference is enabled for local development; set `APP_ENV=production` to disable the docs, ReDoc, and OpenAPI schema by default. Set `ENABLE_API_DOCS=true` only after deliberately deciding to expose them. Match the production frontend with `VITE_API_DOCS_ENABLED=false` so it does not display a broken API-reference link. Build output is ignored by Git and should be regenerated for deployment.

## Dashboard authentication

The browser must never receive `CLOUD_API_TOKEN`.

- With no dashboard credentials configured, dashboard routes only allow loopback clients for local development. Remote requests fail closed.
- For remote deployment, configure all variables server-side:
 - `DASHBOARD_USERNAME`
 - `DASHBOARD_PASSWORD` (at least 12 characters; use a unique, long password)
 - `DASHBOARD_SESSION_SECRET` (at least 32 characters; generate a random value)
 - `DASHBOARD_COOKIE_SECURE=true` for HTTPS deployments
- Generate a session secret using `python -c "import secrets; print(secrets.token_urlsafe(48))"`.
- Configure `CLOUD_API_TOKEN` as a separate long random secret for device-to-cloud ingestion.
- Put public deployments behind HTTPS and restrict network access. Do not expose the local demo token.

Partial dashboard-auth configuration deliberately disables dashboard access until corrected. Never put these server-side credentials in `frontend/.env`, a `VITE_*` variable, React bundle, or Git.

## Checks

From the repository root:

```powershell
python -m pytest -q
```

From `frontend/`:

```powershell
npm run lint
npm run typecheck
npm test
npm run audit
npm run build
```

The first successful `npm install` generates `package-lock.json`. Commit that lockfile to GitHub and use `npm ci` for clean/reproducible installs thereafter. Do not commit `node_modules/` or `frontend/dist/`.

Frontend type checking, Vitest, and the production build must be run in an environment that can install packages from npm. A syntax parse is not a substitute for those checks.

## Limitations

- The dashboard is an engineering observation UI, not a clinical monitoring product. Browser-only refresh and appearance preferences are stored in local storage; credentials are never stored there.
- Device metrics require the API host to access the configured device database. API-host resource metrics are not automatically Raspberry Pi measurements.
- The development fixture is for local use only. Final acceptance requires the official MayaCardio mock/checker, ARM64 validation, physical power-cut testing, deadline verification, long-outage recovery, resource measurements, and demo evidence.
- Public deployment requires a real hostname, HTTPS/reverse proxy, strong secrets, and a deployment review.


## Appearance, PWA installation, and viewport behavior

- Light/dark appearance is shared by the public pages and monitoring dashboard. The selection is stored in the browser under `mayacardio.theme`.
- The homepage includes a small draggable install control. On browsers that dispatch `beforeinstallprompt`, it opens the native install flow. Where that event is unavailable, it explains the browser menu path instead of pretending installation succeeded.
- The app manifest, icons, and service worker support PWA installation. The worker caches the app shell and static assets, and deliberately does not cache dashboard/API responses.
- The document viewport is fixed. Navigation and dashboard chrome stay in place while content scrolls inside the relevant workspace. On small screens, the homepage can scroll within its content pane to keep all controls reachable.
- During local development, the service worker is registered on `localhost` and `127.0.0.1`; use a private browser profile or clear the site's service worker if testing stale development assets.
